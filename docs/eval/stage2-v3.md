# 段2を増やしたデータで学習し直した記録（#55、v1.1.0）

#41 で用意した学習データ（`docs/training-data.md`）で段2を GPU で学習し直し、今のモデル（`stage2-model-v1`）と比べた記録。
配布物のモデルを、16 万例で学習したモデル（`stage2-model-v2`）に入れ替えた。

A は句ごとの完全一致（1 位が正解）、B は句ごとの 1 ページ目（9 件以内に正解。#39 で目標に選んだ測り方）。

## 結論

- **A は上がった。** ATC 2026 の句・子音だけで 19.3% → **24.2%**（+4.9 ポイント。今のモデルが外して新しいモデルが当てた例 229、その逆 53）。
- **B は動かない。** 36.9% のまま。段2が並べ替えるのは段1の上位 8 件だけなので、1 ページ目（9 件）に入る候補の顔ぶれは、
  モデルを変えても同じ（ATC の 9,932 例すべてで一致を確かめた）。
- **文脈の効果はごく小さい。** ATC の句・子音だけで、文脈ありの A は 24.2%、なしは 24.0%。
- **丸暗記は見られなかった。** 学習に使った文の前半を渡しても、後半をそのまま出した例は 500 文中 0 件。
- **次の壁は段1。** ATC の句・子音だけでは 52.3% の例で、段1の候補 32 件に正解がない。ここは段2では取り返せず、B の上限は 47.7% になる。

## データの量ごとの伸び

GPU（RTX A4000）で、学習データから `--train-sample` で無作為に選んだ例を倍ずつ増やした。dev はどの段階でも同じ 20,000 例
（`--dev-sample 20000`）で、top-1 は段1の候補に正解がある 4,917 例について数えた。どの段階も 4 エポック流れ、途中で打ち切られず、
最後のステップがいちばんよかった。

| 学習の例 | dev の top-1 | decision loss | 前の段階からの伸び | 学習の時間 |
|---|---|---|---|---|
| 20,000 | 43.5% | 4.856 | — | 1.2 時間 |
| 40,000 | 47.5% | 4.085 | +4.0 ポイント | 1.6 時間 |
| 80,000 | 52.0% | 3.557 | +4.5 ポイント | 2.7 時間 |
| 160,000 | 57.3% | 3.126 | +5.3 ポイント | 4.8 時間 |

**伸びが止まる前に、ユーザーの判断で 160,000 例で止めた**（性能を見るため）。終える条件（伸びが 0.5 ポイント未満）には届いていないので、
データを増やせばまだ伸びる可能性がある。増やすときは、このモデルを `--base` にして続きから学習する（ユーザーの選択。手順は
`docs/training-gpu.md` の「6. データを増やして続きから学習する」）。

この表の top-1 は、今のモデルの記録（dev 57.8%、`docs/eval/stage2-trained.md`）とは dev の例が違うので比べられない。比べるのは次の節の数字。

文脈がある例は ATC で 9,932 例中 7,128 例、test で 2,736 例中 336 例（test は文どうしを続けていないので少ない）、固有名詞は 0 例。

## 段2に渡す候補の数

B を動かすには、段2に渡す候補を 9 件より多くする必要がある。新しいモデルで候補の数を変えて測った（今の既定は 8）。
遅延は 1 回の変換（段1＋段2）の p50 と p95。開発機（aarch64、2 スレッド）で 3 つの計測を同時に流した値で、Windows の実機とは違う。

| 候補の数 | ATC 句・子音だけ：A | B | 母音あり：A | B | test 句・子音だけ：A | B | p50（ATC 子音だけ） | p95（ATC 子音だけ） |
|---|---|---|---|---|---|---|---|---|
| **8（既定）** | 24.2% | 36.9% | 34.4% | 52.6% | 25.0% | 32.6% | 230 ms | 420 ms |
| 16 | 25.2% | 40.2% | 35.0% | 56.5% | 26.0% | 35.2% | 350 ms | 683 ms |
| 32 | 25.5% | 43.5% | 34.7% | 58.3% | 26.6% | 37.2% | 581 ms | 1,181 ms |

16 件と 32 件は今のモデルでは測っていないので、B の伸びのうちモデルの寄与は切り分けられていない。候補の数を増やすと、
キー入力が止まってから候補が確定するまでの待ち時間が延びる（打っている間の表示は段1だけなので変わらない）。
**既定の 8 は変えない**（ユーザーの判断）。増やすかどうかは、Windows の実機で遅延を測ってから決める。

新しいモデルは今のモデルと構成もファイルサイズも同じなので、8 件のときの遅延はほぼ変わらないはず（今のモデルの遅延は今回測っていない）。

## 候補ウィンドウを開く割合（margin）

温度が 3.44 → 2.87 に変わるので、確率の差（margin）の閾値 0.1 の振る舞いも変わる。段2を使った入力で margin が 0.1 未満なら、ライブ変換を
更新せずに候補ウィンドウを開く（#11）。ATC の句・子音だけ（3,557 例、段2を使うのは 2,826 例）で測った：

| モデル | 開く割合（全入力に対して） | 開くときの段2の 1 位の正解率 | 開かないときの段2の 1 位の正解率 |
|---|---|---|---|
| 今（温度 3.44） | 44.8% | 8.7% | 16.8% |
| 新（温度 2.87） | 31.8% | 9.9% | 24.1% |

開く回数は減り、開かないときの正解率は上がる。開くときの 1 位はほとんど誤っているので、閾値 0.1 の考え方（`docs/eval/stage2-trained.md`）はそのまま通じる。閾値は変えない。

## 過学習と丸暗記

学習に使った例と使っていない例（dev）で同じことを測った（`data/scratch` の使い捨てのスクリプト。本文は記録せず集計だけを見た）。

**文の丸暗記。** 正解が 30 文字以上の途中で切っていない文を 500 文ずつ選び、前半を渡して貪欲法で続きを生成した。渡し方は 2 通り：
前半を文脈として渡す（入力は空）／入力（スケルトン）全体と候補の前半を渡す（学習と同じ形）。

| モデル | 例 | 渡し方 | 後半をそのまま出した | 後半の先頭 10 文字が一致 | 一致した文字の割合 |
|---|---|---|---|---|---|
| 新 | 学習に使った文 | 文脈 | 0 件 | 0 件 | 0.02% |
| 新 | 使っていない文 | 文脈 | 0 件 | 0 件 | 0.00% |
| 新 | 学習に使った文 | 入力と前半 | 0 件 | 0 件 | 1.32% |
| 新 | 使っていない文 | 入力と前半 | 0 件 | 0 件 | 1.20% |
| 今 | 学習に使った文 | 入力と前半 | 0 件 | 0 件 | 0.85% |
| 今 | 使っていない文 | 入力と前半 | 0 件 | 0 件 | 0.81% |

学習に使った文でも使っていない文でも差がなく、学習した文をそのまま覚えて出すことは見られなかった。配布物のモデルは段1の候補を並べ替えるだけで、
文を生成しない（#40 の判断）ので、この確認は「モデルが学習の文を抱えていないか」を見るためのもの。

**並べ替えの汎化の差。** 例を 1,500 ずつ選び、例の候補（最大 32 件）を並べ替えた top-1：

| モデル | 学習に使った例 | 使っていない例 |
|---|---|---|
| 今 | 34.3% | 33.1% |
| 新 | 69.3% | 55.7% |

（「今」のモデルは、どちらの例も学習していないので差がないのが自然。）新しいモデルには 13.5 ポイントの差があり、学習の例に寄っている面はある。
ただし、使っていない例の top-1 が 33.1% から 55.7% に上がっていて、dev も最後のステップまで良くなり続けたので、過学習で悪化している様子はない。

## 判断

**入れ替える。** 基準 4（A が上がり、B が下がらなければ入れ替える）を満たす：ATC 2026 の句・子音だけで A は 19.3% → 24.2%、B は 36.9% のまま。

基準 4 は、測定のあとでユーザーの判断で変えた。元は「B が上がり、A が下がらなければ」だったが、上位 8 件の並べ替えでは B はモデルで動かないので、
文字どおりでは満たせなかった。基準を置いたときにこの点を見落としていた。B を上げるには、段1の候補に正解が入る割合を上げるか
（B の上限そのものが上がる）、段2に渡す候補を増やす（遅延と引き換え）必要がある。ユーザーの選択で、次は段1に取り組む。

入れ替えの内容：`scripts/fetch-stage2-model.sh` を `stage2-model-v2` に変えた。温度は 3.44 → 2.87。閾値（候補 8 件、コスト差 500、margin 0.1）は変えない。

## 計測の手順

```bash
# 例は #39 と同じ（docs/eval/errors.md の「計測の手順」で作った target/eval/atc.jsonl、test.jsonl、proper.jsonl）
# 今のモデルは data/stage2、新しいモデルは data/stage2-v3/out/160000（scripts/fetch-stage2-model.sh で取れる）
docker compose run --rm dev bash -c '
  for f in atc test proper; do
    uv run --project python python -m aiokey analyze --examples target/eval/$f.jsonl --dict build/aiokey.dic \
      --scorer <モデルのフォルダ>/aiokey-stage2-q8_0.gguf [--no-context] [--max-candidates 16] \
      --rows target/eval/v55/$f-rows.jsonl > target/eval/v55/$f.json
  done'
```

遅延は、同じ例で `Analyzer.rank` の時間を測った。dev コンテナ（MS-R1、aarch64、CPU 2）で、ATC の 1 回が約 45 分、test が約 15 分、固有名詞が約 1 分。
