# 段2で打った子音に合う文を生成する試作（#40、v1.0.3）

#39 で、誤りの約 7 割は段1の候補（32 件）に正解がないとわかった。段1の候補を並べ替える今の段2では取り返せないので、
段2に文を生成させ、打った入力に合う文字列だけを残す方式（azooKey の zenzai に近い）を試作して、目標の測り方
（B：句ごとの 1 ページ目、A：完全一致）と速さを測った。IME の挙動は変えていない。

## 結論

**本番には入れない。** 生成だけでは、ATC 2026 の句ごと・子音だけで 1 位が正解なのは 0.5%（今の方式は 19.0%）。
生成の候補を今の方式に足しても、良くなった例は 1 件もなく、1 位は 19.0% → 17.7%、1 ページ目は 36.6% → 34.0% に下がる。
速さも、生成だけで p50 683 ms（今の方式の約 3 倍）かかる。

生成の仕組み（制約つきのビームサーチ）は動き、段1の 32 件にない正解を出せる例もある（`zyq/F/knd` → ジョン・F・ケネディ、
ATC の「アインシュタイン・リングと呼ばれます。」「メンタル・アカウンティングとは、」）。外れた例の約 7 割は、ビームサーチが
最大にしている値（段2の log P − 段1のコストの罰）そのものが、正解より外れた文を高く見ている。段1のコストを足さないと、
今度は正解のほうが値が高いのにビームサーチの途中で落ちる。どちらに振っても当たらないのは、学習済みの段2が候補の並べ替えだけを
学んでいて、文を左から 1 トークンずつ書く力が弱いため（下の「生成が当たらない理由」）。
生成方式を続けるなら、段2を生成用に学習し直す（#41）のが先。

## 方式

- **今の方式**：段1（K = 32）の 1 位と 2 位のコスト差が 500 以上なら段1の並び、迷うときは段1の上位 8 件を段2で並べ替え、
  残りを後ろにつなぐ（サーバーと同じ。#39 の `analyze` と同じ手順）。
- **生成だけ**：学習済みの段2（stage2-model-v1、Q8_0、aiokey 形式。プロンプトは文脈とスケルトンだけで、読みを含まない）で、
  ビームサーチで文を生成する（`Scorer.generate`、`crates/aiokey-scorer/src/generate.rs`）。
  - 制約：生成した文字列をバイトごとに段1のラティスの語（辞書の語と、辞書にないかな 1 文字。かなはカタカナも）の表記に
    当てはめ、どれかの語の途中か語の切れ目にいる間だけ続けてよい。漢字の表記も、段1の辞書の読みのスケルトンが入力と合うとき
    だけ許される。終わり（EOS）は入力の末尾の切れ目でだけ許す。語彙のトークンはバイトのトライに並べ、制約に合わない枝は刈る。
  - 並べる値：段2の log P の和 − 重み × 段1の語のコストの和 ÷ 500。重みは 0.5、ビームの幅は 8（下の「設定の探索」）。
- **合わせた**：段1が迷わない（コスト差 500 以上）ときは今の方式のまま。迷うときは、段1の上位 8 件と生成の候補を合わせて段2で
  採点して並べ、残りの段1の候補を後ろにつなぐ。

  出したのは 2 例（上の 2 句）だけで、どちらも段1が「迷わない」（コスト差 500 以上）と判定したため、合わせた方式では

  段2はその並びを正しいカタカナ語にまとめられないうえ、文が長いぶん外れやすい。

## 生成が当たらない理由

ATC の句ごと・子音だけの全 3,557 例（文脈あり、ビームの幅 8、段1のコストの重み 0.5）で、生成が外れた理由を分けた
（`analyze.generation_errors`、`compare --errors`）。正解がラティスの語でつくれるかを確かめ、つくれるなら、正解と生成の 1 位を
ビームサーチと同じ並べる値（段2の log P − 0.5 × 段1の語のコストの和 ÷ 500。語のコストは表記をつくれる語の並びの最小）で比べた：

| 理由 | 例 | 割合 | 意味 |
|---|---|---|---|
| 正解 | 18 | 0.5% | 生成の 1 位が正解 |
| 制約で出せない | 295 | 8.3% | 正解がラティスの語の並びでつくれない（辞書にない読み・数字の読みなど。段1でも出せない） |
| 探索の誤り | 616 | 17.3% | 正解の並べる値のほうが高いのに、ビームサーチで落ちた |
| 並べる値の誤り | 2,628 | 73.9% | 生成の 1 位の並べる値のほうが高い（探しきっても正解を選ばない） |

段1のコストの重みを変えると、誤りの種類が入れ替わる（先頭 200 例、外れた 180 例の内訳）：

| 段1のコストの重み | 探索の誤り | 並べる値の誤り |
|---|---|---|
| 0（段2の log P だけ） | 122 | 58 |
| 0.25 | 77 | 103 |
| 0.5（既定） | 37 | 143 |
| 1.0 | 28 | 153 |

- **段2の log P だけで並べると、探索で落ちる。** 学習済みの段2は、かなを 1 文字ずつ並べる文に、出だしでは高い確率をつける。
  漢字の語は 1 トークン目の確率が低いので、出だしの数トークンでビームから落ちる。最後まで書いた文どうしでは正解のほうが
  確率が高い（例：`tqzyubnprdxksth、` の正解「誕生日のパラドックスとは、」が −58.3、生成の 1 位
  「てんじょうべにぽるだっかしては、」が −67.5）のに、そこまで残らない。
- **段1のコストを足すと、並べる値そのものが外れを選ぶ。** 出だしのかなの並びは減るが、（見立て。確かめていない）生成した文の多くは段1の辞書のかなの語
  （助詞・活用語尾など、コストの低い語）でつくれるので、コストの罰で正解との差がつかず、段2の log P の差で外れが勝つ。
- どちらも、段2が「候補の並べ替え」（どれが正解か）だけを学習し、文を書く損失（LM 損失）は重み 0.1 でほとんど学んでいない
  （1 トークンあたり 4.6〜5）ことから来ている。並べ替えには十分でも、生成には弱い。
- 正解の log P は、正解を段2のトークナイザーでふつうに切ったときの値。生成はトークンの切り方が違う並びを出すことがあるので、
  比べる値はビームの中の値と少しずれる。

## 設定の探索

ATC の句ごと・子音だけの先頭 200 例で、生成だけの正解率を比べた（重複除去を直したあとのコード、1 プロセスずつ）。
どの設定でも 1.5% 以下で、今の方式（同じ 200 例で 1 位 15.5%、1 ページ目 36.5%）に遠く及ばない。

| 設定 | 完全一致（1 位） | 候補に正解がある | p50 |
|---|---|---|---|
| 段1のコストの重み 0（段2の log P だけ） | 1.0% | 1.5% | 763 ms |
| 重み 0.25 | 1.0% | 1.0% | 688 ms |
| **重み 0.5（既定）、ビームの幅 8（既定）** | 1.0% | 1.0% | 686 ms |
| 重み 1.0 | 0.5% | 0.5% | 709 ms |
| 重み 0.5、ビームの幅 32 | 1.0% | 1.0% | 1,895 ms |
| 重み 0.5、ビームの幅 64 | 1.0% | 1.5% | 3,181 ms |

- 重みは、正解率がほぼ同じなので、出だしのかなの並びを抑えられる 0.5 にした（0 より速い）。
- ビームの幅を広げると時間は 3〜5 倍になるが、正解率は上がらない。幅 64 でも探索の誤りは 37 → 29 例にしか減らず、
  並べる値の誤りが増える（143 → 151 例）。
- ラティスの語からカタカナの読み（辞書にないかなのカタカナ版）を除いても、変わらなかった（重複除去を直す前に試した）。

## 速さ

キー入力から候補までの時間（dev コンテナ、CPU 2 スレッド、Q8_0、aarch64）。ATC の句ごと・子音だけの先頭 300 例を
方式ごとに別のプロセスで測った（文脈あり）。同じプロセスで続けて動かすと、前の方式の採点で計算したプロンプトの KV を
次の方式が使い回し、時間が低めに出る。

| 方式 | p50 | p95 | 同じ 300 例の 1 位 | 1 ページ目 |
|---|---|---|---|---|
| 今の方式 | 227 ms | 412 ms | 15.3% | 34.7% |
| 生成だけ | 683 ms | 1,226 ms | 0.7% | 0.7% |
| 合わせた | 912 ms | 1,710 ms | 14.7% | 31.3% |

**暫定目標（50 ms）は、どの方式も満たさない。** 今の方式も、段2を使う入力では目標を超えている（#8 の記録と同じ。
サーバーはキー入力に段1の候補をすぐ返し、段2は入力が止まってから裏で動かす）。生成は今の方式の約 3 倍、目標の約 14 倍。
合わせた方式は、迷う入力で段2の並べ替えと生成の両方をするので、いちばん遅い。

遅い理由（内訳は測っていない。仕組みからの見立て）：

- 生成は 1 トークンごとに段2を 1 回動かす（ビーム 8 本をまとめて 1 回）。かなはほぼ 1 文字 1 トークンなので、
  句（平均 17 文字）で十数〜二十回になる。今の方式は候補 8 件をまとめて 1 回で採点する。
- 各段で、ビームごとに語彙のトライをたどって制約に合うトークンを列挙し、ビームの KV をコピーしている。

速くする案（生成の正解率が上がってから試す）：

- **語ごとに伸ばす。** ビームをトークンではなくラティスの語で伸ばし、語の複数トークンを 1 回にまとめて計算する
  （段2を動かす回数が語の数まで減る）。探索の誤り（出だしで漢字の語が落ちる）にも効く見込み。
- 段1が迷うときだけ生成する（合わせた方式と同じ）。ただし ATC の句（子音だけ）で段1が迷わない
  のは 21%（3,557 句のうち 748 句）しかなく、8 割の入力で生成が要る。
- キー入力をまたいで、ビームと KV を使い回す（打ち足した分だけ伸ばす）。
- 量子化を下げる（Q4）、小さいモデルに蒸留する、x86_64 で AVX2 を使う（#14）。

## 判断

**生成の方式は本番に入れない。IME の挙動は変えない。** 生成だけでも、今の方式と合わせても、正解率（B：句ごとの 1 ページ目、
A：完全一致）が今の方式を下回り、速さも目標から遠い。

- 試作の道具（`Scorer.generate`、`Converter.lattice_words`、`python -m aiokey compare`）は残す。段2を学び直したあとに、
  同じ例で測り直せるようにするため。
- 生成方式に戻るなら、先に段2を生成に使えるように学習する（#41 で学習データを増やすときに、LM 損失の重みを上げる・
  生成用の損失を足す）。そのうえで、語ごとに伸ばす探索を試す。
- 正解率を上げるいちばんの近道は、今のところ段1の候補を増やす側（#39：誤りの約 7 割は段1の候補に正解がない）。
  その 1 つとして、文の途中の `/` のあとが長いと「・」の候補が段1に入らない問題を #52 に切り出した
  （ATC の「・」を含む 47 句がすべて落ちている）。

## 計測の手順

```bash
docker compose run --rm dev bash -c '
  # 例は #39 と同じ（docs/eval/errors.md の「計測の手順」で作った target/eval/atc.jsonl と proper.jsonl）
  uv run --project python python -m aiokey compare --examples target/eval/atc.jsonl --unit phrase \
    --scorer data/stage2/aiokey-stage2-q8_0.gguf --rows target/eval/gen-atc-rows.jsonl > target/eval/gen-atc.json
  uv run --project python python -m aiokey compare --examples target/eval/proper.jsonl \
    --scorer data/stage2/aiokey-stage2-q8_0.gguf > target/eval/gen-proper.json'
```

- 生成は時間がかかる。ATC の句の 7,114 例は、ファイルの順に 5 つずつ振り分けて（i 番目の例を i mod 5 番目の組へ。
  文脈は例ごとに持っているので、分けても変わらない）5 つの `compare --unit phrase` を並列に動かし（約 3.5 時間）、
  割合だけを例の数で重みをつけてまとめた。並列に動かした回の時間は使わず、速さは下のとおり方式ごとに 1 プロセスで測り直した：

```bash
docker compose run --rm dev bash -c '
  uv run --project python python -m aiokey compare --examples target/eval/atc.jsonl --unit phrase --consonants-only \
    --limit 300 --methods generate --scorer data/stage2/aiokey-stage2-q8_0.gguf > target/eval/gen-latency-generate.json'
# 今の方式・合わせた方式も --methods current / combined で 1 つずつ。外れた理由は --errors（生成だけを含むとき）
```

- 固有名詞の 40 文は「、」を含まないので、句ごとと文が同じになる。上の表は #39 と同じく「文」の行（母音を足す乱数も #39 と同じ）。
