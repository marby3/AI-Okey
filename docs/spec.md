# AI-O Key（あいおーきー）仕様書

AI-O Key は、**子音だけで入力することを前提にした日本語 IME** である。

## 概要

子音だけのローマ字入力を、辞書による候補生成と小型AIによる採点の2段で日本語文に変換するIMEを作る。実行サイズは全体で100MB前後、CPUのみで動くことを目標とする。

- 入力：母音を省いたローマ字（子音スケルトン）。ア行の母音はそのまま残す。
- 変換：段1が辞書とn-gramで候補を出し、段2の小型モデルが文脈込みで最も自然な候補を選ぶ。
- 方針：完全ローカル動作。文章は生成せず候補から選ぶので、入力した子音と矛盾する出力は出さない。
- 補助：曖昧な箇所だけ母音を打てる混在入力に対応する。
- 対象環境：Windows（TSF）。

## 入力規則

子音は行ごとに1文字に揃え、「ん」と「っ」には専用キーを割り当てる。n だけで「ん」を表すと「な行」と区別できず、精度に最も響くためである。

| 対象 | 入力 | 例 |
|---|---|---|
| か行〜ぱ行 | 行ごとに子音1文字（k s t n h m y r w g z d b p） | か・き・く → k |
| し・ち・つ・ふ・じ | 行の子音に揃える | し → s、ち・つ → t、ふ → h、じ → z |
| ア行 | a i u e o をそのまま | う → u |
| ん | 専用キー q | ほん → hq |
| っ | 専用キー x | まって → mxt |
| 拗音 | 子音 + y | きょ → ky |
| 長音 | - | ラーメン → r-mq |
| を | w（わと共通） | を → w |

入力例：はたしてほんとうに → `htsthqtun`

混在入力：どのかなも通常のローマ字（ka など）で打ってよい。母音が付いた部分は確定情報として候補を絞り込む。

### 英語の混在入力

モードを切り替えずに英単語を混ぜて打てるようにする。英単語はつづりどおりに打つ。段1が英単語の経路も候補に加え、段2が文脈から日本語と英語のどちらかを選ぶ。

- 英単語辞書：コーパスに出てくる英字表記の語（英単語・略語）を頻度付きで集め、つづりそのものを検索キーにして段1の辞書に加える。例：keyboard → keyboard。スケルトンとしての解釈も同時に候補に残る。
- 生の入力：入力した英字列そのものを常に候補に含める。
- 学習データ：コーパス中の英字表記はスケルトン化せず、つづりのまま入力側に残す。これで段2が、日本語の文脈に英単語が入るパターンを学習する。
- 明示指定：確実に英語にしたい語は / で始める（SKKの略語入力と同じ考え方）。自作キーボードなら専用キーでもよい。
- 英文だけを打つとき：英数キーで直接入力モードに切り替える（通常のIMEと同じ）。
- 単語間の空白：変換中のスペースキーは変換に使うので、英単語の後の空白は Shift + Space で入れる。

q（ん）と x（っ）は英単語のつづりにも現れる。英単語の経路はつづりのまま辞書を引くので衝突はしないが、queue のような語では両方の解釈が候補に並ぶ。

## システム構成

段1が辞書だけで候補を絞り込み、段2の小型モデルがその中から1つを選ぶ。確定した文は次の入力の文脈になり、KVキャッシュも再利用される。

### 段1 候補生成

AIを使わず、辞書とn-gramだけで上位K件（初期値32）の候補を数ミリ秒で出す。

1. スケルトン索引辞書：辞書の全見出しについて、読みを入力規則でスケルトン化する。スケルトンから単語リストを引くトライ（ダブル配列）を事前に構築する。例：htst → 果たして
2. ラティス構築：入力の各位置で辞書を引き、単語ラティスを作る。未知語に備えて、子音を各段のかなに展開したひらがなの経路も残す。
3. ビーム探索：Mozcの変換エンジンと同じく、単語コストと品詞連接コストで探索し、文全体の上位K件（N-best）を出す。
4. 文節単位の処理：長い入力は文節境界で区切る。確定した部分は段2の文脈に回す。

出力：候補文（漢字かな混じり）、その読み、段1のコスト。

### 段2 AI採点器

段1の候補をOpenJev方式で採点し、確率が最も高いものを第1候補にする。文章を生成しないので、出力は必ず入力スケルトンと一致する。

- ベースモデル：zenz-v2.5-xsmall。かな漢字変換に特化したGPT-2系のモデルで、パラメータ数は22.5M、トークナイザーは文字単位＋バイト単位BPE。
- 入力形式：確定済みの文脈、スケルトン、候補の順に並べ、zenzの入力形式に倣って専用の区切りトークンで区切る。
- 採点：候補ごとに log P(候補 | 文脈, スケルトン) を計算し、候補集合の上でsoftmaxして確率分布にする。
- 高速化：文脈とスケルトンの共通接頭辞は1回だけforwardし、そのKVキャッシュを全候補で共有する。候補部分だけをバッチ処理する。文脈部分のキャッシュはキー入力をまたいで再利用する。
- 確信度：1位と2位の確率差（margin）を使う。閾値を下回ったら、ライブ変換を保留して候補ウィンドウを開く。

## 学習

コーパスから（スケルトン, 正解文）の組を自動生成し、候補集合上の負の対数尤度でベースモデルの全パラメータを再学習する。

データ生成の手順：

1. コーパスを集める（Wikipedia、青空文庫など。ライセンスは個別に確認する）。
2. SudachiまたはMeCabで形態素解析し、読みを付ける。
3. 入力規則に従って読みをスケルトン化する。
4. 段1で候補を生成し、正解を含む候補集合を作る。正解が候補から漏れた例は、段1の改善用に記録しておく。
5. 水増しする：一部のかなに母音を残す（混在入力向け）、途中で切る（ライブ変換向け）、文脈ありとなしを混ぜる。

損失関数：OpenJev の decision_loss と同じく、候補集合上のlog softmaxに対する負の対数尤度を使う。Brierスコアの加算は任意とする。補助として、正解文の言語モデル損失を混ぜることも検討する。

学習環境：パラメータ数が22.5MなのでLoRAは使わず、GPU 1枚で全体を学習する。学習後は温度スケーリングで確信度を校正する。

## 実行環境と性能目標

全体を100MB前後に収め、キー入力から候補表示までを50ms以内にすることを目標とする。いずれも目標値で、実測して見直す。

| 項目 | 目標 |
|---|---|
| モデル | 約25MB（8bit量子化GGUF） |
| 辞書＋bigram | 数十MB |
| 合計 | 100MB前後 |
| 推論 | CPUのみ（llama.cpp） |
| 応答時間 | 50ms以内（キー入力から候補表示まで） |

## 評価と開発ステップ

最初の判断材料は、段1の候補再現率である。正解がK件の候補に入っていなければ、段2がどれだけ優秀でも当てられない。

評価指標：

- 段1の候補再現率（正解がK件に含まれる割合）
- 文単位のtop-1／top-5正解率
- 打鍵数の削減率（通常のローマ字入力との比較）
- 応答時間（p50／p95）、英単語を含む文での正解率

## リスクとライセンス

- 「ん」「っ」を専用キーにしないと、精度が大きく落ちる可能性がある。
- 1〜2文節の短い入力は文脈が足りず当たりにくい。候補ウィンドウから選ぶUIを前提にする。
- zenzはCC-BY-SA 4.0で公開されているので、派生モデルを配布する場合も同じライセンスを継承する。
- 辞書とコーパスのライセンスも個別に確認する。

## 仕様からの変更点

元の仕様書から、開発計画を立てる段階で次のように変えた。

### 土台は Mozc ではなく azooKey-Windows のフォーク

元の仕様では Mozc をベースに composer、辞書、リライターを差し替える予定だった。開発コストと PC の負荷を比べ、azooKey-Windows（MIT）をフォークする形に変えた。

- azooKey-Windows の TSF クライアント（Rust）、名前付きパイプ上の gRPC、インストーラーを流用する。
- 変換エンジン（Swift）と設定アプリ（Tauri）は外し、自作の変換エンジンに差し替える。Bazel、Swift、Node は不要になる。
- Mozc からは辞書と連接コストの**データ**を使う。Mozc 内部がひらがなキーを前提にしている問題（元の仕様の「要調査」）は、これで避けられる。
- 挙動は AI-O Key の仕様を優先し、azooKey の仕様は必要に応じて変える。
- UI は Mozc を可能な範囲で再現する。候補ウィンドウは WebView2 をやめ、Win32 ネイティブで描く。Mozc の設定ダイアログは当面再現せず、設定は TOML で行う。

### 実装言語は Rust

条件は「実装コストが低いこと」と「実行時の負荷が低いこと」で、Rust 自体は必須ではない。フォーク元の TSF とサーバーが Rust であること、GC がなく辞書を mmap で読めることから Rust を選んだ。データ生成と学習は Python で行い、変換エンジンは PyO3 経由で Python から呼ぶ。

### ほかの OS への展開を前提にした構成

変換エンジンは OS に依存しないクレートにし、Linux でもテストする。OS ごとのフロントエンド（当面は Windows の TSF だけ）は、同じサーバーと gRPC プロトコルにつなぐ。サーバーは Windows では名前付きパイプ、unix ではソケット（UDS）で待ち受ける。

### 混在入力の未決事項

`ka` を「か」と読むか「k行＋あ」と読むかは、ラティスで両方の解釈を試すことにした。どちらを採るかは段1のコストと段2の採点が決める。

### スケルトン化の追加規則（仮決定）

元の仕様の表にないかなは、次のように仮に決める。参考にできる前例がないため、後で変えることがある。

| かな | スケルトン |
|---|---|
| ぢ・づ | d |
| ゃ・ゅ・ょ | y（拗音） |
| 小書きの ぁ・ぃ・ぅ・ぇ・ぉ・ゎ | 出力しない（ファ → h、ティ → t） |
| ヴ | b |
| 小書きの ヵ・ヶ | k |
| ゐ・ゑ | w |
| 記号・数字 | そのまま |

### 開発環境

開発は Docker の dev コンテナを前提にする。Windows 向けバイナリは cargo-xwin でクロスビルドし、正式なリリースビルドは GitHub Actions の Windows ランナーで行う。学習はレンタルの GPU サーバーで、使うときだけ起動して行う。
